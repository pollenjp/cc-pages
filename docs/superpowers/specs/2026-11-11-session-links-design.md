# 会話のトップページにリンクを残す (`cc-pages link`) の設計

- 日付: 2026-11-11
- 状態: 承認済み (方針をユーザーが承認した。この文書はその書き写し)
- 対になる変更: 呼ぶ側 (このマシンでは dotfiles の Claude Code の Stop hook と status line)。呼ぶ側との約束は「契約」の節

## 何のためか

Claude Code の footer は、設定 `footerLinksRegexes` に当たったリンク (PR・チケット・cc-page のページなど) をバッジで出す。
バッジは今の branch の PR を含めて 5 個までで、新しいものが入ると古いものから消える (Claude Code の本体が決めていて、設定では
増やせない)。長い会話では、前に出た PR やページを footer から辿れなくなる。

そこで、会話に出たリンクを cc-pages の会話のトップページ (`/p/<session>/`) に全部残せるようにする。footer の側には、そのページへの
入口を 1 つだけ常に出す (status line に置く。呼ぶ側の仕事)。入口の URL は session id しか使えないので、session id から会話の
トップページを引ける URL も cc-pages に足す。

cc-pages が受け持つのは「渡されたリンクを会話ごとに残し、トップページに描く」ことだけ。どのリンクを拾うかは呼ぶ側が決める
(このマシンでは、Claude Code の Stop hook が footer と同じ規則で transcript から拾って渡す)。

## ゴール

1. `cc-pages link` で、会話にリンクを足せる。同じ URL は 1 つにまとまり、同じ入力を何度渡しても結果は変わらない
2. 会話のトップページに「リンク」の節が出る
3. `GET /s/<session_id>/` で、その会話のトップページへ飛べる
4. 一覧 (`/`) の会話の行にリンクの数が出て、検索 (絞り込み) でリンクの label と URL も引ける

## やらないこと

- リンクを消す・隠すコマンド (要るようになってから足す)
- リンクの題を外から取ってくること (PR の題を GitHub に聞くなど。ネットワークと認証が要り、遅くなる)
- cc-pages が transcript を読んでリンクを拾うこと (拾うのは呼ぶ側。cc-pages は Claude Code の内部の形式に縛られない)
- 終わった会話をまとめて埋める道具

## してはいけないこと

- `cc-pages link` が遅い・止まる。呼ぶ側は会話の turn の終わりごとに打つので、ふつうの入力 (数件〜数百件) なら数十 ms で返す
- 呼ぶ側のおかしな入力 (http でない URL・巨大な入力・制御文字) で、トップページが壊れる・危ないリンクが描かれる
- 今の `new`・`status` とページの振る舞いが変わる

## 契約 (呼ぶ側との約束)

呼ぶ側 (dotfiles の hook) はこの節だけを頼りに作る。変えるときは両方を合わせて変える。

### `cc-pages link`

```
cc-pages link --session <session id> --stdin
cc-pages link --session <session id> --url <URL> [--label <文字>] [--group <文字>] [--source assistant|tool] [--at <RFC 3339>]
```

- `--session` は必須。`new`・`status` と同じ検証 (文字・数字・`-` だけ) をする
- `--stdin` を付けると、標準入力から JSON Lines を読む。1 行が 1 件で、形は次のとおり

  ```json
  {"url": "https://github.com/o/r/pull/12", "label": "r#12", "group": "PR", "source": "assistant", "at": "2026-11-11T15:06:01.234Z"}
  ```

  | キー | 要るか | 意味 |
  | --- | --- | --- |
  | `url` | 必須 | 絶対 URL。scheme は http か https だけ。2048 字まで |
  | `label` | 任意 | 表示の文字。無い・空なら URL を出す |
  | `group` | 任意 | 組の名前 (自由な文字。呼ぶ側は `チケット`・`PR`・`cc-page` などを渡す)。無い・空なら `その他` |
  | `source` | 任意 | `assistant` (Claude の応答の文に出た) か `tool` (tool の出力に出た)。無ければ `assistant` |
  | `at` | 任意 | そのリンクが出た時刻 (RFC 3339)。無ければ今 |

- `--stdin` を付けないときは、`--url` などの flag で 1 件を渡す (手で足すとき・試すとき)。キーの意味は上と同じ
- 同じ呼び出しの中に同じ URL が何度出てもよい (出るたびの `at` を渡してよい)
- 成功したら stdout に 1 行の JSON を出し、終了コード 0

  ```json
  {"url": "http://localhost:7777/p/20261111-0a1b2c3d/", "added": 3, "updated": 5, "skipped": 0}
  ```

  `url` は会話のトップページ。`added` は新しく足した URL の数、`updated` は前からあった URL のうち時刻か出どころが変わった数、
  `skipped` は捨てた件数
- 捨てる件: JSON として読めない行・`url` が無い・http(s) の絶対 URL でない・長すぎる・`source` や `at` が読めない。捨てた件ごとに
  理由を stderr に 1 行出し、ほかの件は残す (1 件のために全部を捨てない)。flag で渡した 1 件が捨てる件なら、stdout には何も出さず
  終了コード 1 (`status` の検証エラーと同じ扱い)
- 終了コード 1 は、session id の検証エラー・ファイルの読み書きの失敗・flag の誤りのとき。呼ぶ側は 0 でなければ何もせず次に回す
- 会話のディレクトリが無ければ、`status` と同じ規則で作る (`session.json` の骨も書く)
- 残す件が 0 (空の入力・全部捨てた) なら、会話のディレクトリを作らず何も書かずに終了コード 0。stdout の `url` は、会話のディレクトリが
  あれば `/p/<dir>/`、無ければ `/s/<session_id>/`
- 空の行は件に数えない (捨てた件にも数えない)。`label` は 200 字、`group` は 50 字で切る
- 1 行は 64 KiB まで (超えた行は捨てて `skipped` に数える)。1 回の入力は 16 MiB まで (超えた分は読まない)。呼ぶ側は 1 回に渡す量を
  16 MiB より十分小さく分けて打つ (目安は 1 回 1 MiB まで)
- 書いたら、動いている serve に知らせて、その会話だけを読み直させる。知らせの応答は待たない (`new`・`status` の `NotifyTouch` は
  全体の走査を終えるまで待つので使わない。下の「速さ」)。serve が居なければ、定期走査で拾われる

### まとめ方 (同じ URL)

- URL は前後の空白を落とした文字列で比べる (正規化はしない。呼ぶ側が同じ形で渡す)
- 前からある URL に来たら: 最初の時刻は小さい方、最後の時刻は大きい方にし、出どころ (`assistant`・`tool`) は和にする
- `label`・`group` は最初に入ったものを残す。前のものが空 (URL を出していた・`その他` だった) で新しい件に値があれば埋める

### `GET /s/<session_id>/`

- session id が一致する会話があれば、`302` でその会話のトップページ (`/p/<session>/`) へ送る
- 無ければ `404` で、「この会話のページ・リンクはまだありません」と、一覧へのリンクだけのページを返す
- `/s/<session_id>` (末尾の `/` なし) も同じに扱う (`/` 付きへ送ってよい)
- session id の文字が `new` の検証に通らなければ 404

## 置き場所と形 (cc-pages の中のこと)

- 会話のディレクトリに `links.json` を置く。`session.json`・`status.json` とは分ける (`status.json` を分けたのと同じく、
  書き込みがぶつからないように)。書くのは `cc-pages link` だけ

  ```json
  {
    "schema": 1,
    "updated_at": "2026-11-11T16:38:00+09:00",
    "links": [
      {"url": "…", "label": "TKT-12", "group": "チケット", "sources": ["assistant", "tool"],
       "first_seen": "2026-11-11T15:06:00+09:00", "last_seen": "2026-11-11T16:38:00+09:00"}
    ]
  }
  ```

- 同じ会話に 2 つの `cc-pages link` が同時に来ても、片方の書き込みが消えないようにする (会話のディレクトリの lock ファイルを
  排他で取ってから読み・まとめ・書く)。serve が書きかけを読まないよう、一時ファイルに書いて rename する
- 1 つの会話に残すのは 5000 件までにする。超える新しい URL は捨てて (`skipped` に数え) stderr に出す
- 走査 (`Scan`) は `links.json` の更新時刻も見て、変わったら読み直す (`status.json` と同じ)

## 速さ

`cc-pages link` は会話の turn の終わりごとに打たれる。今の作りのままだと次の 2 つが重い (spec を読み直したときに見つけた)。

- `NotifyTouch` は応答を最大 100 ms 待ち、受けた serve は全体の走査 (`RefreshAll`) を終えてから返す。全体の走査は、変わった
  transcript (このマシンには 50 MB を超えるものが 7 本、最大は約 170 MB) を頭から読み直す
- `findOrMakeSessionDir` は呼ぶたびに全部の会話の `session.json` を読む。リンクが出た会話はみな会話のディレクトリを持つようになるので、
  数が増え続ける

そこで:

- `link` の知らせは、応答を待たずに返り、serve には全体の走査ではなく、その会話のディレクトリだけを読み直させる (知らせの口と
  読み直しの作りは作る人が決める。`new`・`status` の `NotifyTouch` と全体の走査の振る舞いは変えない)
- 会話のディレクトリを引くときは、名前 (`<日付>-<session id の先頭>`) が session id の先頭と合うものだけの `session.json` を読む
  (全部は読まない。合うかの最後の決め手は今までどおり `session.json` の `session_id`)。`new`・`status` も同じ関数を使うなら、
  そちらも速くなるだけで振る舞いは変わらない

## トップページの「リンク」の節

```
リンク (31)
  チケット
    TKT-12      app.notion.com/p/…                       15:06〜16:38
  PR
    r#11        github.com/o/r/pull/11                   16:20〜16:35
  cc-page
    📄0001      調べたこと                               15:40
  ▸ tool の出力だけに出たリンク (24)
```

- 置き場所は「ページ」の節の後ろ。リンクが 1 件も無い会話には節を出さない
- 組 (`group`) ごとにまとめる。組の並びは、組の中で一番早い最初の時刻の順。組の中は、最後の時刻の新しいものを上にする
- 出どころに `assistant` を含む件を上に出し、`tool` だけの件は節の最後の `<details>` (畳んだまま) に、同じ組分けで入れる
- 1 行には、label (リンク)・添え書き・時刻を出す
  - 添え書き: URL が cc-pages 自身のページ (`/p/<session>/<page>/`) なら、索引にあるそのページの題。ほかは scheme を除いた URL を
    短くしたもの
  - 時刻: 最初と最後 (同じなら 1 つ)。日付が会話の始まりの日と違えば日付も付ける
- リンクは http(s) のものだけを `<a>` にする (書くときに検証済みでも、描くときにもう一度確かめる)。外へのリンクには
  `rel="noopener noreferrer"` を付ける

## 一覧 (`/`)

- 会話の行に、ページの数と並べてリンクの数を出す (0 なら出さない)
- 絞り込みの対象に、リンクの label と URL を足す
- ページが 0 でリンクだけの会話も一覧に出る (今も `status` だけの会話は出る。同じ扱い)

## README と skill

- README に `cc-pages link` (契約の節の要点) と `/s/<session_id>/` を書く
- plugin の skill (`plugins/cc-pages/skills/cc-page/`) は `cc-pages link` を使わない。skill に書かないなら `skill_test.go` の
  突き合わせも要らない

## こちらで決めたこと (承認の後に決めた細部)

- 契約の入力は JSON Lines にした。hook が 1 回の呼び出しで何件でも渡せ、flag の組を並べるより壊れにくい
- 捨てる件があってもほかの件は残す。turn ごとに打たれるので、1 件のために全部を落とすと取り逃しが続く
- `label`・`group` は最初のものを残す。同じ URL の label が turn ごとに揺れないように
- 5000 件の上限を置く。呼ぶ側の不具合で `links.json` が膨らみ続けないように
- リンクの無い会話に「まだありません」は出さない。hook を使わない人の会話に毎回出てしまうため
- `/s/` の 404 は、session id を画面に出さない (出すなら html/template で escape する)
- `link` の知らせは待たず、その会話だけを読み直させる。turn ごとに全体の走査が走らないように (「速さ」)

## 作りながら決めたこと (実装の細部)

- 渡す件が 0 のときの振る舞い・空の行の数え方・`label` と `group` の長さは、最終レビューで呼ぶ側から見える振る舞いだと分かったので、
  呼ぶ側と合わせて契約の節に書き足した。stdout の例の host も、実際の出力 (new・status と同じ `BaseURL()` の `localhost`) に直した
- 1 行と 1 回の入力の上限も、呼ぶ側と合わせて契約の節に書き足した。上限で読むのをやめると、呼ぶ側は書き込みの途中で EPIPE を受け、
  失敗と見なして渡し直し続けうるため、呼ぶ側は 1 回に渡す量を小さく分けて打つ
- 0 件で会話のディレクトリを作らないのは、呼ぶ側はリンクの無い会話でも打ちうるため (作ると一覧が空の会話で埋まる)。`/s/<session_id>/`
  は、後で何かが書かれればトップページへ飛ぶ入口
- 空の行を数えないのは、JSON Lines の末尾の改行や空行はふつうにあるため。「JSON として読めない」には、オブジェクトでない行・
  キーの型が違う行も含める
- `--stdin` と `--url` は一緒に使えない。`--label`・`--group`・`--source`・`--at` は `--url` と一緒に使う。余分な引数も flag の誤り
  (終了コード 1)
- 何も変わらなければ書かない (links.json・session.json の mtime を動かさない) し、serve にも知らせない。呼ぶ側が turn ごとに同じ組を
  渡し直しても、serve が毎回その会話を読み直さないように。`at` を渡さない件は毎回「今」が入るので、渡し直すと最後の時刻が進む
- `updated` は契約どおり時刻か出どころが変わった数で、label・group を埋めただけでは数えない (ファイルは書き直す)
- label・group を切るときは末尾を `…` にする。制御文字は空白に替え、空白の並びは 1 つにする。URL と同じ label と `その他` の
  group は空として持つ (後から来た値で埋まる)
- URL は前後の空白を落とすだけで書き換えない。中の空白・制御文字・壊れた UTF-8 は捨てる件。日本語などの非 ASCII は通す
  (cc-pages new の URL はパスの日本語を %XX に潰さない)
- 長すぎる行は捨てて続きを読む。1 回の入力の上限を超えたら、そこで読むのをやめて stderr に 1 行出す (読まなかった分は `skipped` に
  数えない)
- 手で壊した links.json は `links.json.broken` に退けて、空から書き直す (stderr に 1 行)。JSON の文法の崩れだけでなく、時刻の文字列の
  崩れも同じに扱う。失敗を返し続けると、呼ぶ側は失敗を黙って捨てるので、誰も気づかないまま取り逃す。読めないとき (権限など) だけが
  終了コード 1
- links.json の lock は会話のディレクトリの `links.lock` (flock)。3 秒取れなければ終了コード 1。flock を使うのは linux と darwin で、
  ほかの OS では lock しない (build が通ることだけを保つ)
- まだディレクトリの無い会話への最初の書き込みが重なると、片方が作られたばかりで session.json の無いディレクトリを別の会話と見て
  名前を伸ばし、会話のディレクトリが 2 つに割れていた (前からある競合で、link が同時に 2 つ来ると起きる)。作るときだけ
  `<root>/sessions.lock` を握って探し直し、作ったらすぐ session.json の骨を書く。あれば lock は取らない
- session.json も一時ファイルに書いて rename する。link が turn ごとに書くので、切り詰めてから書くと、その隙に読んだ側が空の JSON を見る
- 知らせの口は `POST /_/touch/{session}` (`{session}` は会話のディレクトリ名)。serve はその会話のディレクトリだけを読み直し、
  transcript は読み直さない (題などは最後の走査のものを使い、次の定期走査で追いつく)。送る側は request を書いたら接続を閉じる
- `/s/<session_id>/` は索引に無ければディスクも探し、あればその会話を読み直させてから送る (知らせが届かなかったときも、
  定期走査を待たずに入口が開く)
- 「会話の始まりの日」は、session.json の first_seen・ページの作成時刻・リンクの最初の時刻のうち最も早いもの
- 添え書きの URL は scheme を除き、%XX を戻して、60 字で切る。label の無い件は、その URL を label の位置に出して添え書きは空にする。
  cc-pages 自身の会話のトップページ (`/p/<session>/`) へのリンクには、その会話の題を添える
- 自分の cc-page かどうかは、URL の port が serve の port と同じで、host が `localhost`・`127.0.0.1`・`::1` か bind の host であることで見る
- 一覧の検索の placeholder に「リンク」を足した

## 確かめること

- store: まとめ方 (最初・最後の時刻、出どころの和、label を残す)、捨てる件、5000 件の上限、同時に 2 つ打ったときに消えないこと
- CLI: `--stdin` と flag の両方、stdout の JSON、終了コード
- server: 「リンク」の節 (組・並び・畳む・添え書き)、`/s/` の 302 と 404、一覧の数と絞り込み、`javascript:` などの URL を描かないこと
- 走査: `links.json` だけを書き換えたときに、定期走査で拾われること
- 速さ: `link` が serve の応答を待たずに返ること、知らせで全体の走査が走らないこと、会話が多くても全部の `session.json` を読まないこと
- 実物: `cc-pages link` で足したリンクが、serve の会話のトップページに出ること
